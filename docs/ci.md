# CI/CD

## Contract

CI/CD is an orchestration layer around Gear operations.

A CI provider must not duplicate build or deployment logic. Its responsibilities are limited to:

1. repository checkout;
2. running validation and packaging commands;
3. persisting release artifacts between jobs;
4. providing credentials and deployment configuration;
5. invoking the generic Deployer runner.

Buildkite is the current reference implementation, not a platform dependency.

## Current Buildkite flow

Normal builds run:

```text
Build, smoke & package ─────┐
                            ├── manual deploy approval
Dependency audit ───────────┘
                                   ↓
                              deploy artifact
```

The build job executes:

```bash
./ops/test
./ops/smoke
./ops/package
buildkite-agent artifact upload "dist/*"
```

The audit job executes:

```bash
./ops/audit
```

Audit currently reports independently and is configured as a soft failure.

The deploy job depends on the build job and the approval block; the approval
block also waits for the audit job. Because audit is a soft failure, an audit
failure does not prevent approval.

The deploy job downloads the artifact created by the build job and invokes:

```bash
./ops/ci/deployer deploy -v
```

It never rebuilds the release.

## Deployment policy

Deployment is currently:

- limited to `main`;
- manually approved;
- serialized so that deploy and rollback cannot run concurrently against the same target.

The current test-site deployment uses a Buildkite concurrency group with a limit of one.

## Manual rollback

Rollback is an explicit Buildkite operation rather than a permanently waiting step in every normal build.

A manual build from the Buildkite UI on `main` can be started with:

```text
DEPLOY_ACTION=rollback
```

That build skips normal build/audit/deploy work, asks for rollback approval and then executes:

```bash
./ops/ci/deployer rollback -v
```

## Buildkite secrets

### Gitea checkout

Private Gitea repositories use the Buildkite secret:

```text
GITEA_SSH_KEY
```

`checkout.ssh_secret` must be configured on every command step that checks out the repository.

It must also be configured on the bootstrap "Load pipeline" step in the Buildkite UI, because Buildkite must clone the private repository before it can read `.buildkite/pipeline.yml`.

### Deployment

The deployment job uses:

```text
WP_GEAR_DEPLOY_CONFIG
MAIN_SSH_KEY
```

`WP_GEAR_DEPLOY_CONFIG` contains the deployment profile, such as host, user, port, deployment root, document root, target adapter and remote PHP CLI path.

`MAIN_SSH_KEY` contains the private SSH key used by the deployment target.

`ops/ci/deployer` materializes both secrets into temporary files, sets restrictive permissions, invokes `ops/deployer`, and removes the temporary files afterward.

## Artifact handoff

Build and deploy may run on different agents.

The `.tar.gz` and `.sha256` generated by `ops/package` are uploaded as Buildkite artifacts and downloaded by the deploy job.

This guarantees that the release deployed is the same artifact produced by the validated build job.

## Gitea integration status

Gitea remains the source-of-truth repository.

The current Buildkite integration does not yet provide a general bidirectional Gitea integration.

Pending work includes:

- automatic Gitea → CI triggering;
- portable CI → Gitea commit-status reporting.

Those integrations are convenience/automation layers, not requirements for building or deploying Gear.

Renovate automerge is disabled. It can be reconsidered after successful CI
status can be reported back to Gitea in a provider-portable way.
